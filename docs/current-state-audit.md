## Existing architecture

- **Framework:** Next.js 16.3.0 App Router, React 19.2.8, TypeScript, Tailwind CSS 4.
- **3D:** Three.js 0.185.1 rendered through React Three Fiber 9.7.0; Drei 10.7.7 provides environment, sky, and instancing helpers.
- **Physics:** `@react-three/rapier` 2.2.0 with a fixed `1/60` physics timestep.
- **State:** Zustand 5.0.14. Game HUD and lifecycle state, auth, and graphics presets use separate stores.
- **Validation:** Zod 4.4.3 validates route metadata and route geometry at build/server load time.
- **Data mode:** mock mode is the working mode. Auth, attempts, favourites, leaderboard data, and routes are local/browser-backed. The Supabase facade is deliberately a stub and must remain safe when credentials are absent.
- **Route delivery:** route JSON is statically imported by `lib/routes/route-registry.ts`; the game page is statically generated. The browser does not make route-data requests during play.
- **Bundle boundary:** `GameCanvas` is dynamically imported only for `/play/[slug]`, preserving the non-game page loading boundary.

## Current rendering approach

`GameCanvas` creates a WebGL `Canvas` with ACES tone mapping, a capped DPR range, basic antialiasing controls, directional sunlight, hemisphere/ambient light, sky, fog, and a Drei city environment map.

`RouteWorld` samples a Catmull–Rom centreline and produces:

- a visual road, markings, kerbs, and pavements;
- a large flat ground collider and repeated cuboid edge colliders;
- simple route-specific landmarks;
- building visuals from bounding boxes around footprint vertices;
- canvas-generated brick, concrete, and glass facade textures;
- instanced lamps and trees.

This is a valid prototype renderer, but it is not a geographically grounded city renderer. Most buildings are axis-aligned bounding boxes rather than footprint extrusions. Road and terrain elevation are flattened to `y = 0`; `roadPoint.y` and banking are not used by the sampler.

## Current physics and camera approach

The vehicle uses one Rapier rigid body with a cuboid collider and locked pitch/roll. `applyArcadeDriving` decomposes velocity into forward and lateral components, writes velocity directly each tick, applies an exponential lateral-grip approximation, and smooths a target yaw rate. It is an arcade controller, not a wheel/suspension vehicle model.

Known limitations:

- Mass, centre of mass, tyre front/rear balance, suspension travel, longitudinal slip, aerodynamic drag, body roll, and pitch are not modelled separately.
- A high-level fixed ground collider avoids falling through the road, but cannot follow future elevation or kerb collision accurately.
- The current yaw-rate controller is not derived from a steering angle/wheelbase model, so its turning circle will not feel physically consistent.
- The camera uses a low-stiffness spring (`springK = 7`) with velocity accumulation, which can lag behind a rapidly accelerating car. It allocates temporary vectors every render frame and has no collision avoidance.
- Only chase and hood views exist. There is no close/far chase choice, bonnet/cockpit camera, collision raycast, or player-controlled camera sensitivity.

## Current route format and data sources

`RouteData` stores local road coordinates, checkpoints, simple buildings, scenery, basic metadata, and a string attribution field. The current Canary Wharf JSON explicitly identifies itself as generated by `seed-local-data` and uses `source: "procedural"` for its buildings.

The existing seeding script generates fictional Catmull–Rom loops and algorithmically places rectangular buildings and scenery around them. It states that they are **not digital twins**. Route latitude/longitude acts only as an area label; it is not used to derive local geometry.

Consequently, the current OSM attribution is not enough to establish a real-data provenance chain. There is no:

- original WGS84 road geometry;
- local-projection metadata;
- OpenStreetMap element identifiers or raw cache;
- real building footprint source;
- elevation sample source;
- source manifest;
- source/playable geometry split; or
- recorded gameplay adjustment list.

## Current settings and pause behaviour

`settings-store.ts` persists only Low, Medium, and High quality presets in localStorage. The settings that genuinely affect the renderer are DPR cap, shadow enablement/map size, draw distance, scenery density, fog distance, and antialiasing.

Current gaps:

- `drawDistance` is not applied by `RouteWorld`, so it is a dead configuration value.
- No Ultra/Custom preset, resolution scale, ambient occlusion, bloom, reflections toggle, texture quality, vehicle/building detail, frame cap, fullscreen, display, controls, audio, accessibility, or diagnostics settings exist.
- Escape is recognised in `InputSampler`, but `Vehicle` reads only `cameraPressed`; it never uses `pausePressed`. Therefore Escape does not currently toggle the pause menu.
- The pause overlay has no focus trap, confirmations, settings sections, or explicit input-routing policy beyond the `paused` physics flag.

## Testing coverage

Coverage is missing for:

- elevation ingestion and terrain attachment;

- gamepad/keyboard focus loss and stuck-input clearing;

- browser-level regression tests for login, guest mode, route opening, pause/resume, and exit.

No Playwright/browser test runner is currently configured.

## Performance and visual limitations

No browser profiler trace, FPS trace, draw-call count, triangle count, texture memory measurement, or route load measurement exists yet. Production build timing above is the only baseline measurement.

Main technical bottlenecks and risks:

- Each building is rendered as multiple individual meshes. Building textures are cloned per building.
- The world is unchunked and has no building LOD.
- The road, pavement, and kerbs allocate geometry from sampled splines but do not support terrain or junction meshes.
- The camera makes per-frame vector clones.
- Landmark and water visuals are hard-coded by route slug.
- Environment-map use depends on an external preset request; there is no explicit asset manifest or offline fallback.
- There are no GLB/GLTF vehicle assets in `public`; the car is assembled from primitive meshes, hence its visibly blocky appearance.

## Proposed minimum additional dependency

No package needs to be installed for Milestone A. For Milestone B, propose only:

- `proj4` and `@types/proj4` — a tested coordinate-reference implementation for WGS84 to a metre-based local/UK projection. This avoids inventing a geographic projection formula.

Native `fetch`, Zod, Node filesystem APIs, and current Three.js tooling cover the remaining B-stage requirements. No heavy map SDK, terrain renderer, vehicle controller package, or image provider package is proposed.

## Risks and rollback plan

1. **Overpass availability/rate limits:** all retrieval will be a developer script with timeout, retry, configurable endpoint, and on-disk cache. Gameplay will consume generated files only.
2. **Incorrect road access or route complexity:** validate OSM access tags, one-way state, layers, bridges, and junction topology before publishing the route. Do not represent estate/private or pedestrian-only geometry as drivable.
3. **Data provenance:** raw response, source element IDs, licences, generation version, and all gameplay adjustments will be retained. OSM attribution must be paired with actual source records.
4. **Schema migration:** add optional versioned fields and keep the current mock routes valid until they can be migrated intentionally.
5. **Performance regression:** preserve static imports and dynamic canvas loading; add draw/triangle/FPS instrumentation before high-detail city content.
6. **No current Git repository:** create a backup archive or initialise a repository before the first generated-route replacement. This is the immediate rollback safeguard.

## Proposed genuine Canary Wharf route candidate

Candidate: a roughly 0.9–1.2 km closed-road race conversion using public-road segments around **West India Avenue, Bank Street, Upper Bank Street, and Heron Quays Road**, near Canary Wharf / Heron Quays DLR.

Why it is suitable:

- it is an identifiable Docklands office district with genuine high-rise footprints;
- Bank Street and West India Avenue are mapped named roads with public-transport context;
- the candidate lies near the target coordinates and has wide urban corridors, several bends, and recognisable dockside/modern-office character;
- it avoids claiming the current fictional loop is real.

This is a **candidate only**. Milestone B must query and validate exact OSM ways, access status, directionality, levels, and total length before selection. If those checks show unsuitable access or multi-level complexity, the pipeline must choose and document an alternate nearby OSM-backed route rather than forcing this shape.

## Milestone B acceptance criteria

Milestone B passes only when:

1. A selected Canary Wharf route is generated from cached OSM responses; no game page calls Overpass.
2. The generated record stores original WGS84 geometry, origin/projection metadata, element IDs, raw-cache references, and an ODbL attribution manifest.
3. The playable geometry is derived from—not substituted for—the source geometry.
4. Every smoothing, width, barrier, checkpoint, spawn, and junction change is recorded in `gameplayAdjustments`.
5. Generated local coordinates pass deterministic projection, deviation, curvature, minimum segment, discontinuity, and self-intersection validation.
6. Nearby building polygons originate from the cached OSM data and retain height/source-confidence metadata, even before the later building-visual milestone.
7. A development-only debug overlay compares source and playable centrelines and visualises checkpoints and footprint outlines.
8. Existing mock auth, favourites, attempts, route pages, and the other two routes remain functional without credentials or a live API.
9. New pipeline tests pass, existing tests still pass, lint is clean, and the production build succeeds.
10. Manual browser verification confirms the generated route loads from local cached/generated data after network access is disabled.
